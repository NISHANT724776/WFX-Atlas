Accounts Payable — Posting & Payments

Feature: wfx-erp-product-fa · Owner: Varun Kumar (VP - Technology)

Functional specification for the development team, generated from the product-team-approved Product Mock Studio screens (feature library wfx-erp-product-fa). The mock is intentionally lenient; this specification is not — it is the contract the development team builds from before it goes to QA and live production. Because the product team was not available for the pre-finalization question batch, this document ADOPTS the proposed defaults as ASSUMED (marked where used); each is listed in Section 8 for sign-off.

Overview

Purpose

Accounts Payable (AP) takes a supplier-side document from “validated” through to “paid”. This feature covers that pipeline across just two screens. A single status-aware screen, AP Posting & Payments, lets the AP clerk post validated documents to the ledger, schedule their expected payment dates, and gather dated documents into payment batches — without leaving the screen. A second screen, Payment Batches, is the register where a Draft batch is released (Confirm Payment) or cancelled. Four payable document types flow through: Supplier Invoice, Credit Note (a negative payable), Expense Invoice, and Advance.

Who uses it

  • AP clerks / accountants — post validated documents, assign expected payment dates, and assemble payment batches (all on one screen).
  • AP / finance managers — confirm (release) or cancel payment batches.
  • Downstream / reporting — read the resulting ledger entries and payment status; they do not act on these screens.

Where it sits in the ERP?

The feature lives in the Finance & Accounting module (real target: libs/angular/features/wfx-erp/wfx-erp-fa). In the Product Mock Studio it is mounted at /accounts-payable under the app base href /wfx-erp-product/, menu label “Accounts Payable” (icon pi pi-wallet). It is downstream of purchasing/GRN (which produce the documents) and upstream of the cash/bank and general-ledger modules (which the postings and payments feed).

Scope of this spec: the two AP screens (AP Posting & Payments, Payment Batches) and the shared AP document detail right-panel. Document capture/validation (Draft → Validated) and the GL posting engine itself are upstream/downstream and out of scope (Section 7).

Navigation rules

  • The two screens are sibling menu links under Accounts Payable. There is no forced wizard — the clerk works the stage they need via the Status filter on S-1.
  • List → detail panel: on S-1, clicking the Doc No link (data-action="open-doc") opens the shared right drawer (S-3). On S-2, clicking the Batch No link (data-action="open-batch") opens the batch detail drawer.
  • Drawers are dismissible (X / overlay / hide); they never navigate away from the list.
  • Documents move between stages by status, not by routing: after any action the list reloads and the acted-on rows drop off if they no longer qualify for the current Status filter.
  • Browser/page titles come from the route title: “AP Posting & Payments”, “Payment Batches”.

Back-navigation / list-state retention (search, filters, sort, page, the From/To range) is not preserved by the mock across drawer opens or re-entry. The real screens must restore list state on return (QA checklist §5) — see Q-11.

Screen specifications

AP Posting & Payments (S-1)

Purpose: one status-aware list covering the AP pipeline up to payment. A Status filter chooses the stage; the toolbar actions follow the current selection, so the clerk posts, schedules, and batches from a single screen.

Layout

  • Page header: breadcrumb “Accounts Payable”, title “AP Posting & Payments”, subtitle, and the selection-driven action buttons (top right).
  • Content toolbar: quick-search input (“Search by doc no. or supplier”), a Status filter, the Expected Pay From/To range filter (Posted view only), and a Doc Type dropdown.
  • Grid inside a surface card; floating filter row; pagination footer (page sizes 20/50/100, default 20).

Status filter & views

  • The Status filter has two options — To Post (Validated) and Posted — and defaults to Validated. Clearing it shows both stages at once.
  • The Expected Pay Date column shows whenever Posted documents can appear (Posted view or the cleared “both” view); it is hidden in the Validated-only view.
  • Switching the Status filter clears the current selection so the action buttons stay honest. Only Validated and Posted documents ever appear on this screen (Draft/In Batch/Paid do not).
  • The list is ordered with dated documents first (ascending by expected date, which helps batching), then undated documents.

Expected Pay From / To range filter

  • Two separate date fields (From, To) plus a Clear button (shown once either is set), visible only when Posted documents can appear (Posted or cleared view). They let the clerk club everything due in a window before selecting.
  • The range is inclusive on Expected Pay Date; the pickers cross-constrain (From’s maxDate = To, To’s minDate = From) so From ≤ To always holds (V-9). Documents without an expected date are excluded while a range is set.

Post & UnValidate (Validated selection)

  • Post (primary): confirmation M-2, then each selected document moves Validated → Posted; the GL date already on the document is kept. Success M-3, selection cleared, list reloaded. Writes are strictly sequential (D-2).
  • UnValidate (secondary): confirmation M-5, then each moves Validated → Draft and leaves this screen. Success M-6. Note F-3: no screen in this feature lists Draft documents, so an unvalidated document currently has no re-validation path — Q-2.

Assign Expected Payment Date (Posted selection)

  • Modal “Assign Expected Payment Date”; helper “Set the expected payment date for {n} selected document(s). Must be today or later.” One required date picker (floor = today, V-5); Assign / Cancel.
  • Assign with no date → warning M-8. On success the date is written to every selected document (sequential); success M-9. If the date is after any document’s Due Date, an additional warning M-10 names those documents but the assignment still proceeds (ASSUMED — Q-3).
  • Assigning a date does not change status; the document stays Posted and now qualifies for the Payment Batch action (T-3).

Create Payment Batch (dated Posted selection)

  • The Payment Batch button appears only for an all-Posted selection where every document already carries an expected date (V-4). Opening the dialog is blocked if the selection spans more than one currency — warning M-12 (single-currency rule, V-7, Q-5).
  • Dialog “Create Payment Batch”: a read-only summary (Documents count, Currency, Batch Total), a required Actual Payment Date picker, and a required Payment Mode select (Bank Transfer / Cheque / Cash / RTGS/Wire / LC / Online). Create Batch / Cancel.
  • Batch Total is the net signed sum of the selected documents, so Credit Notes reduce it (V-10).
  • Submit validates the date (M-13) and mode (M-14). On success a new batch is created in Draft with a snapshot of its member documents, and each member document moves Posted → In Batch (stamped with the batch no, actual date, and mode). Success M-15. The batch is released on S-2.
  • Batch number is PB-{yyyy}-{seq}; in the mock seq is computed client-side (max existing id + 1), which the real server must own (D-4, F-6, Q-6).

Batch detail panel & actions

  • The drawer shows the batch header (Batch No, Status, Payment Date, Payment Mode, Currency, Total Amount, Documents, Created By, Created On) and a read-only “Documents in this Batch” grid built from the stored line snapshot.
  • Footer actions appear only when the batch is Draft (V-11): Cancel Batch (danger) and Confirm Payment (primary).
  • Confirm Payment: confirmation M-18, then the batch and every member document move to Paid (T-5/T-8). Success M-19. In the mock this only flips statuses — the real build must also execute the payment and post the payment GL entry (D-6, Q-8).
  • Cancel Batch: confirmation M-21, then the batch moves to Cancelled and each member document reverts to Posted with its batch fields cleared; the expected payment date is retained so the document can be re-batched (T-6/T-9). Success M-22.
  • Paid and Cancelled batches are terminal — no actions.

Shared AP document detail panel (S-3)

Purpose: a read-only right drawer, opened from S-1, showing one document’s header and its balanced debit/credit journal preview. All state changes live on the parent list — the panel never mutates.

  • Header info: Doc No, Doc Type, Supplier “Name (Code)”, Status (badge), Doc Amount, PO No, GRN No.
  • Dates & Payment: Doc Date, GL Date, Due Date, and — only when populated — Expected Payment, Payment Batch, Actual Payment, Payment Mode, then Created By, Created On.
  • Accounting Entries (Dr / Cr): a grid of journal lines (Account name + code, Debit, Credit; zero amounts blank) with a pinned bottom Total row, then a status line: “Balanced — total debit equals total credit.” (success) or “Not balanced — please review the entries.” (error). The mock data is always balanced (V-12).
  • The panel re-fetches when the document id (or a refreshKey) changes. Note F-5: the parent never bumps refreshKey, so a panel left open across an action can show stale header/status until re-opened.

  • All reads/writes go through one thin per-feature service; components never call HTTP directly. On promotion the mock service is swapped for the real API-backed one and the screens are unchanged.
  • Sequential writes: bulk actions (Post, UnValidate, Assign date, batch create, Confirm, Cancel) write one record at a time (RxJS concatMap). The mock server does read-modify-write per request, so parallel writes to one collection file drop records; the real transactional API should perform each bulk action as a single atomic request (D-2).
  • The server is the source of truth for every rule in Section 6 — client validation is a convenience, not the enforcement.
