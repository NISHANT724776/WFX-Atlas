Sales Orders — Product Mock Spec

Feature: wfx-erp-product-sales · Owner: Vinod Khanna (Technical Architect)

Functional specification for the development team, generated from the finished, product-team-approved Product Mock Studio screens (feature library wfx-erp-product-sales). This document contains ASSUMED answers pending product-team sign-off (see Section 8).

Overview

This document specifies the Sales Orders feature for the real WFX ERP application. It was generated from the finished, product-team-approved mock screens in the Product Mock Studio (feature library wfx-erp-product-sales). The mock is intentionally lenient; this specification is not — it is the contract the development team builds from, and it goes to QA and then to live production.

Purpose

Sales Orders (order confirmations, “OC”) are the commercial head record of the ERP: one order belongs to one buyer, carries a season, currency, manager, total quantity and value, key dates, and free-text fabric/packing instructions. The feature lets the sales/merchandising team create, search, review, confirm, cancel and (within strict rules) delete sales orders.

Who uses it2

  • Merchandisers / sales coordinators — create and maintain orders, enter instructions.
  • Sales managers — review and Confirm orders, cancel with a reason.
  • Downstream teams (planning, production, shipping) — read confirmed order data; they do not edit here.

Where it sits in the ERP

The feature lives in the Sales module (real target: libs/angular/features/wfx-erp/wfx-erp-sales, route /sales). It is the upstream source for production planning, BOM and shipment documents; statuses beyond Confirmed (Part Ship, Shipped, Closed) are driven by those downstream modules, not by these two screens.

Scope of this spec: the Sales Order LIST screen and the Sales Order DETAIL (create/edit) screen, including their shared workflow, data contract, and validations. Order line items (article / size / colourway breakdowns) are not part of the mock and are out of scope (see Section 7).

Navigation rules

  • List → Detail (edit): click the order-number link in the Order column, or right-click a row and choose Edit. Both open /sales/orders/{id}.
  • List → Detail (new): the “+ Add New Order” button in the page toolbar opens /sales/orders/new.
  • Detail → List: the back arrow in the page header returns to /sales/orders. Any pending auto-save is flushed before navigating away; the flush must complete (or fail with an error toast) — a navigation must never silently drop an unsaved change.
  • Unknown order id: an error toast “That sales order does not exist.” is shown and the user is returned to the list.
  • Browser/page titles: “Sales Orders” (list), “New Sales Order” (new), “Sales Order” (edit).

Back-navigation state: the mock does not preserve list state (filters, page) across detail visits. The real screen must restore the list exactly as the user left it — search text, status filter, column filters, sort and page (QA checklist §5). See Q-17/Q-18 in Section 8.

Screen specifications

Sales Order List (S-1)

Purpose: single working list of all sales orders with search, filters, bulk selection, row actions and navigation into the detail screen.

Layout

  • Page header: breadcrumb “Sales”, title “Sales Orders”, subtitle, and a primary “+ Add New Order” button.
  • Content toolbar: quick-search input (“Search by order no. or buyer”) and a clearable, searchable Status dropdown.
  • Grid inside a surface card; floating filter row pinned under the headers; pagination footer always visible (never covered by other UI).
  • Floating selection bar appears when one or more rows are selected, with the selection count, a Clear action, and a Delete action.

Toolbar behaviours

  • Quick search matches Order No (MainOCNum) OR Buyer name, case-insensitive substring, trimmed. Real build: debounce 300 ms and extend to PO Ref (ASSUMED — Q-17).
  • Status dropdown filters to exactly one status; clearable (shows all). Values: Saved, Confirmed, Part Ship, Shipped, Closed, Cancelled.
  • Toolbar filters and in-grid column filters combine (logical AND).

Bulk actions

  • Selecting rows shows the floating selection bar with the count and a Delete button.
  • Bulk delete first validates every selected row against the delete rule; if any row is not deletable the whole action is blocked with a warning naming the blocked orders — nothing is partially deleted.
  • After a successful bulk delete the selection is cleared and the list reloads.

Cancel Order dialog

  • Modal, header “Cancel Order”, helper text “Enter a reason to cancel this order.”, one required Reason textarea (4 rows), buttons OK (primary) / Close.
  • OK with a blank/whitespace reason shows the warning “Reason is mandatory.” and keeps the dialog open.
  • OK with a reason sets Status = Cancelled and stores the reason. The real build stores it in a dedicated CancelReason field with an audit entry (who/when); it must NOT overwrite the order’s Comments as the mock does — flagged, Section 7.2 (ASSUMED — Q-13).
  • Close / X dismisses without changes.
  • Real build addition: the dialog must name the order being cancelled (e.g. “Cancel OC-2026-0001”) — the mock text is generic.

Empty, loading and error states

  • Empty list: grid shows its no-rows overlay. Real build: message “No sales orders found” with an Add New Order call to action (ASSUMED — Q-22).
  • Load failure: error toast “Load Failed — Could not load sales orders.” with retry guidance; the grid stays empty, never silently blank.

Auto-save behaviour

  • Seed fields (all must be filled before the record is created): Ship Under PO Ref, Buyer, Category, Currency, Total Quantity, Total Value. Season, dates and all Instruction-tab fields are NOT seed fields.
  • New order: the record is inserted automatically the moment the last seed field is filled and valid. The server assigns the real order number at this insert (ASSUMED — Q-7); the mock’s client-side “OC-DRAFT-nnnnnn” placeholder must not ship.
  • Existing order: every change is debounce-saved automatically. The mock PUTs the whole record; the real screen PATCHes only the dirty fields (Section 7.1).
  • The save-status indicator in the toolbar shows idle → saving → saved / error. A failed save shows the toast “Save Failed — Could not save the sales order.” and the indicator stays in the error state until a subsequent save succeeds.
  • Navigating back flushes any pending save first (see Section 2).
  • Loaded values never count as dirty — opening an order must not trigger a save.

Validation display

  • Errors appear inline per field once the field is touched, using the standard field-error styling; required fields carry the * marker.
  • Exact rule texts are in Section 6 (Validations master list).

Confirm action

  • Confirm is visible for any existing (already auto-saved) record — including an already-Confirmed one. Re-confirm after an edit is deliberate: in the real app, editing a confirmed order creates a new background version in Saved status, and this same button confirms that version (Section 7.1).
  • Clicking Confirm with an invalid form is blocked with the warning “Please fix the highlighted fields before confirming.” Additional confirm gate: both dates filled (ASSUMED — Q-8) and Total Value > 0 (ASSUMED — Q-4).
  • First confirm dialog: “Confirm {MainOCNum}? A confirmed order can no longer be deleted (it can still be cancelled with a reason from the list).” Yes/No.
  • Re-confirm dialog: title “Re-confirm Order”, text “Confirm the current changes to {MainOCNum}?”.
  • On success: status becomes Confirmed, success toast “{MainOCNum} is now confirmed.”, header badge/title refresh, list reflects the change on return.
