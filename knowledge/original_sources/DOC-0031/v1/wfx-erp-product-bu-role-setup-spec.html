BU & Role Setup — Access Control

Feature: wfx-erp-product-admin (screen group “BU & Role Setup”) · Owner: Varun Kumar (VP - Technology)

Functional Specification for the development team, generated from the finished, product-team-approved Product Mock Studio screens (feature library wfx-erp-product-admin, screen group “BU & Role Setup”). The mock is intentionally lenient; this specification is not — it is the contract the development team builds from, and it goes to QA and then to live production. Items marked ASSUMED are pending product-team sign-off (see Open questions).

Overview

Purpose

BU & Role Setup is the ERP’s access-control workbench. It answers three questions for every person who signs in: where they work (Business Units), what a job can do (Roles = permission bundles), and who holds which role in which Business Unit (Assign User), with optional per-user exceptions. Three masters are maintained here — Business Units, Roles and Users — under one tabbed screen.

Who uses it

  • System / access administrators — define Business Units, author Roles and their permission matrix, and assign roles to users per Business Unit.
  • Every other module — reads the effective permissions to decide what a signed-in user may see and do (enforcement lives in each module, not here).

Where it sits in the ERP

The feature lives in the Admin module (mock library wfx-erp-product-admin, route /admin; on promotion the library drops its -product segment → libs/angular/features/wfx-erp/wfx-erp-admin). It shares the Admin library with the Business Process Engine (specified separately). /admin redirects to /admin/bu-role-setup. The permission model is Module → Resource → Action: six modules (Catalog, Sales, Sourcing, Production, Inventory, Finance), each exposing Transaction screens and List screens as resources, and eight actions (View, Create, Edit, Delete, Approve, Post, Export, Cancel). A List resource is read-only navigation — only View and Export apply to it.

Scope of this spec: the tabbed shell and the List + Detail screens for Business Units, Roles and Users, including the permission matrix, per-user overrides and effective-permission view. Runtime enforcement of permissions inside each transaction is out of scope (Q-11).

Navigation rules

  • Tabs sync to the URL: switching tab writes ?tab=; deep-linking a tab opens it directly. The three slugs are business-units, roles, users.
  • List → Detail (edit): click the primary link cell in a row (BU name, Role name, or the combined User cell), or right-click → Edit. List → Detail (new): the “+ Add” button on each tab.
  • Detail → List: the back arrow returns to the shell with the matching ?tab= preserved. Any pending auto-save is flushed before navigating away — a navigation must never silently drop an unsaved change.
  • Unknown id on a detail route: error toast (M-3 / M-8 / M-14) and the user is returned to the list.
  • Browser/page titles: “BU & Role Setup” (shell); “Business Unit”, “Role”, “User” (edit); the New routes are untitled (fall back to the app title).
  • Back-navigation state: the mock does not preserve list state (filters, page, active tab beyond the slug). The real screen must restore search, filters, sort, page and tab exactly as the user left them (QA checklist §5) — Q-10.

Conventions

Rules referenced throughout the field tables and the Validations master list are defined once here, so no field restates them.

ConventionDefinition
EnforcementThe server enforces every rule; client validation is a convenience, not the enforcement. Every status transition is re-validated server-side.
Auto-saveDetail screens have NO Save button. A debounced engine saves on every change once the record exists. Loaded values never count as dirty (opening a record must not trigger a save). The save-status indicator shows idle → saving → saved / error; a failed save keeps the error until a later save succeeds.
Seed fieldsThe field(s) that must be valid before the record is first inserted. Until then the record does not exist and dependent editors (permissions, assignments, overrides) are disabled.
Text fieldsTrimmed; a mandatory text field must contain at least one non-whitespace character; length hard-stops at the stated maximum.
Company scopeRoles and Business Units are company/tenant-scoped in the real build: lists are filtered to the current company and code/name-uniqueness is enforced within it (Q-9).
Status badgeRendered as a wfx-badge chip, never plain text. Severity: Draft = secondary (grey), Active = success (green), Inactive = warning (amber).
Reference CodeA shared, multi-select tag list applied to a Business Unit and to a User. Codes come from the reference-code master (mock: 8 static values — D-6, Q-1).
Date displayAll dates display via the app-wide WfxDateFormatService (user preference, default dd MMM yyyy) — never a hardcoded locale. Date columns use a date filter (calendar picker; equals / before / after / from–to).
Set InactiveRetiring a record opens a modal with one mandatory Reason textarea (4 rows); a blank reason is rejected (M-2). The reason is stored (mock: in Comments) — real build: a dedicated field with an audit entry (D-4).

Permission matrix

  • A top Module selector bar lists the six modules with “Select all” / “Clear”. Only the modules the user selects appear below for permission editing; an empty selection shows an empty-state prompt. A module that already has grants but is not selected is surfaced as a hidden-grants count so grants are never silently lost.
  • For each selected module, a grid of its resources (rows) × the eight actions (columns) of checkboxes. Actions: View, Create, Edit, Delete, Approve, Post, Export, Cancel.
  • List resources accept only View and Export; the other six action cells are rendered disabled/greyed on a List row and can never be granted (V-7). Transaction resources accept all eight.
  • Grants are stored as a map of Resource code → array of granted action codes; only applicable actions are ever stored. GrantedModuleCount / GrantedPermissionCount are derived from it on save.

Activate

  • Gate: the form is valid AND at least one permission is granted (M-7 / M-8 from the detail; M-9 from the list). Activate/Re-activate confirm dialogs per the messages table.
  • On success Status = Active and the role becomes assignable to users; success toast M-13.

Business Unit Assignments (roles per BU)

  • One row per Business Unit: pick a Business Unit (single-select from the Active BU master), then the role(s) the user holds within it (multi-select from Active roles). “+ Add Business Unit” adds a row; the trash icon removes it.
  • The Roles multi-select is disabled until the Business Unit is chosen. A Business Unit already on the user is blocked from being added twice (M-4) — add the extra roles to the existing row instead.
  • Stored as an array of { BusinessUnitCode, RoleIDs[], RoleNames[] } (one entry per BU).
  • Adding assignments requires the record to exist first (pick a User) — else the guard M-5 fires.

Permission Overrides (grid)

  • A grid, one row per overridden screen. Columns: Module / Transaction (searchable picker of any resource, each screen only once — M-12), Apply Date Range, then one column per action (View … Cancel), then a delete action.
  • Each action cell is a tri-state the user clicks to cycle — (Inherit) → Allow → Deny, colour-coded grey / green / red. Cells for actions that do not apply to a List screen show a muted “·” and are not clickable.
  • Apply Date Range: clicking the cell opens a dialog with a range date-picker; the window (From–To, inclusive) scopes the whole row. Empty = applies always. Captured per Module/Transaction row, so every action override on that screen shares the window.
  • “+ Add Override” adds a row for the first screen not already overridden; the guard M-5 applies before the record exists.
  • Meaning: Allow force-grants a permission no assigned role gives; Deny force-removes one a role grants. Deny always wins. Stored as an array of { ResourceCode, ActionCode, Effect: Allow|Deny, FromDate?, ToDate? } (only Allow/Deny rows are persisted; Inherit stores nothing).

Effective Permissions (read-only)

  • A read-only matrix (accordion per module, resources × actions) showing the net result: union of every role the user holds in any Business Unit, then overrides applied (Deny wins over Allow wins over Inherit). Override cells are tinted green (forced Allow) / red (forced Deny). A granted-count badge sits on the panel header.
  • This view never edits — it reflects the panels above. Note the date range on an override is captured but does NOT currently filter the effective view by today’s date (F-3).

Workflow & status lifecycle

Business Units and Users have two states (Active ⇄ Inactive). Roles have three (Draft → Active ⇄ Inactive), because a role must be authored before it can be assigned.

RoleDraftAuto-saved; being authored; not yet assignable; deletable.
RoleActiveAssignable to users; not deletable; stays editable.
RoleInactiveRetired with a reason; not assignable; editable; deletable; re-activatable.
Business Unit / UserActiveIn use; not deletable via the “Active” guard where applicable; editable.
Business Unit / UserInactiveRetired with a reason (User) ; excluded from the assignable BU / role pickers; re-activatable.

Effective-permission computation

For each (resource, action): start from whether ANY role the user holds in ANY Business Unit grants it (union), then apply overrides — Allow adds, Deny removes, Deny applied last so it always wins. Absence of an override = inherit from the roles. (Real build should also gate by the override’s date window — F-3 / Q-12.)
