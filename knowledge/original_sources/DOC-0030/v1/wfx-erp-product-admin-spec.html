Business Process Engine

Feature: wfx-erp-product-process · Owner: Varun Kumar (VP - Technology)

Functional Specification for the development team, generated from the finished, product-team-approved Product Mock Studio screens (feature library wfx-erp-product-process). The mock is intentionally lenient; this specification is not — it is the contract the development team builds from, and it goes to QA and then to live sproduction. Items marked ASSUMED are pending product-team sign-off (Section 8). 

Overview

Purpose

A Business Process Engine (BPE) is a named chain that ties several ERP transactions together in a fixed order — for example a chain named “Order to Ship” whose steps are Sales Order → Packing List → Shipment. This feature lets a business administrator define, name, sequence, activate and retire these chains. Each step is one Document Type (transaction) plus its Sequence position.

Who uses it

  • Business administrators / process owners — create and maintain chains, sequence the transactions, activate and retire them.
  • Downstream modules — read the active chain definitions to know which transaction follows which (enforcement/execution is out of scope here; see Section 7 and Q-8).

Where it sits in the ERP

The feature lives in a new Process module (real target: libs/angular/features/wfx-erp/wfx-erp-process, route /process; the mock library wfx-erp-product-process drops its -product segment on promotion). A BPE is company/tenant-scoped: each chain belongs to a company and its name is unique within that company (D-2, V-1, Q-2).

Scope of this spec: the Business Process Engine LIST screen and the DETAIL (create/edit) screen, including their shared workflow, data contract, and validations. Actually running or enforcing a chain at transaction time is NOT part of this feature (config-only — Q-8).

Screen specifications

Business Process Engine List (S-1)

Purpose: single working list of all chains with search, a status filter, bulk selection, row actions and navigation into the detail screen.

Layout

  • Page header: breadcrumb “Process”, title “Business Process Engines”, subtitle, and a primary “+ Add New Engine” button.
  • Content toolbar: quick-search input (“Search by name or description”) and a clearable, searchable Status dropdown.
  • Grid inside a surface card; floating filter row pinned under the headers; pagination footer always visible.
  • Floating selection bar appears when rows are selected, with the count, a Clear action and a Delete action.

Toolbar behaviours

  • Quick search matches Name (BPEName) OR Description, case-insensitive substring, trimmed. Real build: debounce 300 ms.
  • Status dropdown filters to exactly one status; clearable (shows all). Values: Draft, Active, Inactive.
  • Toolbar filter and in-grid column filters combine (logical AND).

Bulk actions

  • Selecting rows shows the floating selection bar with the count and a Delete button.
  • Bulk delete first validates every selected row against the delete rule; if any row is Active the whole action is blocked with a warning naming the blocked chains — nothing is partially deleted.
  • After a successful bulk delete the selection is cleared and the list reloads.

Set Inactive dialog

  • Modal, header “Set Process Engine Inactive”, helper text “Enter a reason to set this process engine inactive.”, one required Reason textarea (4 rows), buttons OK (primary) / Close.
  • OK with a blank/whitespace reason shows warning “Reason is mandatory.” and keeps the dialog open.
  • OK with a reason sets Status = Inactive and stores the reason. Real build: store it in a dedicated field with an audit entry (who/when); it must not double as free-text Comments (D-11, Q-7).

Empty, loading and error states

  • Empty list: grid shows its no-rows overlay. Real build: message “No process engines found” with an Add New Engine call to action (ASSUMED — Q-12).
  • Load failure: error toast “Load Failed — Could not load process engines.”; the grid stays empty, never silently blank.

Auto-save behaviour

  • Seed field (must be filled before the record is created): Name. Description and steps are not seed fields.
  • New chain: the record is inserted automatically the moment Name is valid; Status = Draft. Only then does Add Step enable.
  • Existing chain: every change (header fields OR steps) is debounce-saved automatically. The mock PUTs the whole record; the real screen PATCHes header fields and does per-step CRUD (D-10).
  • The save-status indicator shows idle → saving → saved / error. A failed save shows toast “Save Failed — Could not save the process engine.” and stays in error until a later save succeeds.
  • Loaded values never count as dirty — opening a chain must not trigger a save.

Activate action

  • Activate is visible for any existing (already auto-saved) chain — including one already Active (re-activate after an edit; per the product decision an edited Active chain stays Active — T-3, Q-3).
  • Activate gate: form valid, ≥ 2 steps (V-6), and every step has a Document Type (V-4). Failures show M-6 / M-7 / M-8.
  • First activate dialog: title “Activate Process Engine”, text “Activate {BPEName}? It becomes available to run as a chain (it can be set Inactive later, with a reason, from the list).” Yes/No.
  • Re-activate dialog: title “Re-activate Process Engine”, text “Save and re-activate the current changes to {BPEName}?”.
  • On success: Status = Active, success toast “{BPEName} is now active.”, header badge refreshes, list reflects the change on return.
